## 一、本轮三缺陷（真 Key 实测暴露）

| # | 证据 | 根因 | 修复 |
| ---- | ---- | ---- | ---- |
| 1 | 图一：网络可达 66ms ✅｜CORS 预检 `Load failed`｜API Key 认证 `HTTP 0` | **连接测试引擎直连 baseUrl**，未经 `resolveRequestRoot` 同源反代 → bigmodel 被浏览器 CORS 拦 | 引擎 base 改走统一路由；auth 步骤改 `callConfiguredModel`（与聊天同链路同格式） |
| 2 | 图二：详情 `❌ 调用失败：服务可达（输出被截断，连通性正常）` 却整体「全部通过」 | 步骤 label/status 用 `r.success` 判定，结论用 `ok` —— 两者不一致 | 统一以 `ok` 判定；截断场景改 `warn`「连通性验证」 |
| 3 | flash 模型恒「截断」 | **智谱 thinking 默认开启**，32 tokens 全被 reasoning 吃掉 → content 空 | smoke 64 tokens + zhipu `{"thinking":{"type":"disabled"}}` 兜底；「推理参数映射」JSON **真正注入请求体**（此前仅存储） |

**实证**：GLM-5.3 ✅ 真实往返；glm-5.3-flash ✅ 真实往返（此前恒截断）；无 CORS、无 HTTP 0。

## 六、口径

- 连接测试现有**两条实现**（provider-slice 实弹 / connection-test-engine 面板流程），二者已统一走 `callConfiguredModel` + `resolveRequestRoot`，不再分叉
- 智谱 thinking 兜底仅作用于**测试冒烟**；聊天是否关闭思考由模型的「推理参数映射」决定（主控可填 `{"thinking":{"type":"disabled"}}`）
- `deepseek-flash` 等非官方模型名仍会失败——属数据配置问题，诊断会明确提示「模型名不被上游接受」
- Mimosa i18n enterApiKey×2 为 UI 文案误报，口径不变
