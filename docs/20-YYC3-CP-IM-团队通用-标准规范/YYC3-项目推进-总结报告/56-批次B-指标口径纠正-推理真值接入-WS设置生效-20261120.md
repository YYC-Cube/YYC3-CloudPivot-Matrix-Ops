## 一、背景

**【CP-IM】** 落档 55 的差距清单把「数据可信度」列为批次 B：agent 用 CPU 冒充 GPU、温度恒 0、QPS/Token 恒 0；Dashboard 不消费 OpsPanel 推理数据；WS 四项设置只存不用。本批逐项落地。

## 二、B1 · GPU / 温度口径纠正

**问题**：agent 在 macOS 上拿不到 GPU，`gpu` 字段实际是 CPU 利用率，首页「GPU 利用率」直接展示该值（实测 30.3% 实为 CPU）；`temp` 恒 0 被当作真实温度；无数据源的用户节点 `gpu:0` 被计入均值，拉低成 31.8%。

**改法（显式来源标记 + 有证据才统计）**：

| 层 | 改动 |
| ---- | ---- |
| 类型 | `NodeData` 新增 `gpuAvailable?: boolean` / `tempAvailable?: boolean`（缺省视为未知，非「0」） |
| agent | 上报 `gpuAvailable:false`（`gpu` 仍承载真实 CPU，供设备性能页 CPU 口径）、`tempAvailable:false` |
| 派生 | `computeDerived` 只统计**有实时 GPU 证据**的节点：`metrics.gpus`（OpsPanel DCGM 逐卡）或显式 `gpuAvailable===true`；新增 `gpuNodeCount` |
| 首页 | 无 GPU 节点时卡片显示「—」；节点卡 GPU 条对上标记节点显示「—」 |
| 节点详情 | GPU/温度未上报显示「—」并注明原因 |
| 设备性能页 | CPU 均值只取 agent CPU 节点；GPU 均值只取 DCGM；温度排除未上报 |
| 用户维护 | `NodeEditModal` 保存时置 `gpuAvailable/tempAvailable=true`（显式声明值） |
| 报告 | Markdown 报告「平均 GPU」在无 GPU 节点时写「—（无节点上报 GPU）」 |

## 三、B2 · OpsPanel 推理真值接入首页

**问题**：QPS/Token 只读 agent 的 `throughput_history`（常量 0）；模型分布只读节点 `tasks`；OpsPanel 的 `inference.qps / gen_tokens_per_s / avg_latency_s` 只进设备矩阵。

**改法**：

| 项 | 实现 |
| ---- | ---- |
| 新 Hook | `useOpsPanelInferenceHistory`：轮询 `GET /api/metrics/history`（服务端 10s 采样、360 点），映射 `{time,qps,tokens}`，失败保留上次 |
| 聚合 | Dashboard 从 `nodes[].metrics.vllm` 汇总 qps / gen_tokens_per_s / running / waiting / 平均延迟 |
| 六卡 | QPS、延迟、Token 三项在 vLLM 可用时以 OpsPanel 为准；延迟 ≥1s 显示 `46.9s` 而非 `46909ms`；Token <1K 显示 `27 tok/s` |
| 趋势 | vLLM 可用时用服务端历史（真实 QPS/Tokens），否则回退 WS |
| 模型分布 | 带 vLLM 指标的节点按 `running` 计入；WS 断开时不再拿 agent 旧 tasks 凑数；vLLM 在线但空闲时明示「OpsPanel vLLM 在线 · 当前无在途请求」 |

**实测（DGX 正在推理）**：`/api/metrics` → `qps 0 / gen_tokens_per_s 26.92→40 / avg_latency_s 46.896 / running 1 / GPU n1 96% n2 95%`；首页显示 QPS 0、延迟 46.9s、Token 27~40 tok/s、GPU 96%、模型分布 100% nemotron。QPS 为 0 是因该请求尚未完成（qps 取 request_success 差分），Token 速率证明推理真实在跑——两者口径不同，不互相编造。

## 四、B3 · WS 四项设置真正生效 + 心跳

| 设置 | 之前 | 现在 |
| ---- | ---- | ---- |
| WS 地址 | 改后需刷新/重挂载 | 进 effect 依赖，**改端点即重连** |
| 重连间隔 | 固定 5000ms | 取 `wsReconnectInterval` |
| 最大重连次数 | 无限重试 | 取 `wsMaxReconnect`，超限如实置 `disconnected` |
| 心跳间隔 | 从不发心跳 | onopen 起 `setInterval` 发 `{type:"heartbeat"}`，agent 回 `heartbeat_ack`；关闭时清理 |
| 令牌 | 已生效 | 不变（`wsToken` 仍为空则不带走） |

## 五、B4 · 重复主机修复（大小写）

agent 上报 `os.hostname()`（`YYC3-22`），用户清单为 `yyc3-22`——大小写不同被当成两台主机，首页出现 8 台（7 用户 + 1 重复）且均值被污染。`mergeFromWS` 现按小写归一：快照命中用户节点时只取实时字段（gpu/mem/temp/model/tasks/可用性），保留 `role/host/source/wsPort` 等身份信息。实测节点 7 台、无重复。

## 七、本批未做（明确挂账）

1. **WS 单实例化**：Layout/FollowUpPanel/AlertRulesPanel 等各自调用 `useWebSocketData()` 仍会建多条连接（重复摄入风险）。需模块级连接管理器 + refCount，属批次 C 前的独立重构。
2. **温度真实采集**：macOS 需 powermetrics 授权，未授权即 `tempAvailable:false`；不伪造。
3. **本地 Ollama 流量统计**：Ollama 无 Prometheus 端点，QPS/Token 仅 DGX vLLM 可测；本地推理流量仍不计数（如实空态）。
