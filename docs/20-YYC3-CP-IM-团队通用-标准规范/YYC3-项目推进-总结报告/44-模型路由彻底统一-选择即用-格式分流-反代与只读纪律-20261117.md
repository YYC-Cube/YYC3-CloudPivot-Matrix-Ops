## 一、三根因（六图实证锤定）

| # | 现象（主控反馈） | 根因 |
| ---- | ---- | ---- |
| 1 | 浮窗选 deepseek，报错却是「模型调用失败(GLM-5.3)」 | **双数据源**：浮窗的模型选择/Key 存旧 hook `useSettingsStore`（localStorage `yyc3_system_settings`），与 settings-ssot 不同源；且发送链路只读全局 `getActiveModel()`（=GLM-5.3），**忽略浮窗面板选择** |
| 2 | 图二/三：测试显示「连接成功 8ms」，实际对话失败 | **诊断假阳性**：诊断/单测对云端模型传 `baseUrl: ""`，网络可达性/CORS 步骤测的是空 URL，恒「通过」 |
| 3 | 图六：群聊 `Load failed`，URL `open.bigmodel.cn/api/anthropic` | ① GLM-5.3 baseUrl 是 **Anthropic Messages 格式**端点，被当 OpenAI `/chat/completions` 调用（协议不匹配 → 空内容/报错）；② 浏览器直连 bigmodel **CORS 阻断**（实测：bigmodel BLOCKED、deepseek 401 放行） |

## 二、数据源裁定（唯一 SSOT）

| 面 | 定义 |
| ---- | ---- |
| 模型定义（可编辑） | **系统管理 → 模型设置**（UnifiedModelManager，写 `yyc3-provider-slice`） |
| 只读消费面 | AI 智能-模型管理（测试/查看/导出）、AI Family-模型设置（选择/绑定/测试）、AI 浮窗配置（选择/温度/测试）——**不可增删改** |
| 全局偏好（选择态） | settings-ssot（`aiModel`/`aiApiKey`/`aiTemperature`/`aiTopP`/`aiMaxTokens`） |

## 三、修复清单（`4f0e99d`）

### 3.1 选择即用（浮窗）

- AIAssistant **迁移 settings-ssot 单源**（删除旧 `useSettingsStore` 依赖，消除 `yyc3_system_settings` 第二数据源）
- 发送模型解析链：**选中 cm 实体 → ollama-live 在线模型 → 全局 getActiveModel()**
- 实证：点选 deepseek-flash 后发送 → 错误/请求均为 deepseek（`/api/v1/llm/deepseek/v1/chat/completions`），不再是 GLM

### 3.2 API 格式分流（`callConfiguredModel`）

| apiFormat | 请求 | 认证 | 解析 |
| ---- | ---- | ---- | ---- |
| `openai`（默认） | `{root}/chat/completions` | `Authorization: Bearer` | `choices[0].message.content`（含 reasoning 回退） |
| `anthropic` | `{root}/v1/messages` | `x-api-key` + `anthropic-version: 2023-06-01` | `content[].text` |

- `apiFormat` 继承链：模型显式 → 服务商默认 → baseUrl 含 `/anthropic` 启发
- `max_tokens` 由高级设置 `maxOutput` 驱动（默认 2048）
- **空内容三分诊断**：`choices=0`（格式/模型名）· `finish_reason=length`（调大输出）· 空文本（模型名/额度）
- CORS/网络错误明确指向「请走 3118 同源反代或配置代理 URL」

### 3.3 同源反代（路由逻辑）

- 前端 `resolveRequestRoot`：**显式 proxyUrl > 同源反代（http 环境）> 直连**
- 映射：`zhipu → /api/v1/llm/zhipu`、`deepseek → /api/v1/llm/deepseek`
- 服务端 `deploy/server.mjs`：**固定白名单** https 反代（非开放代理），保留认证头、去 origin/referer、双斜杠归一
- 实证：两路 POST 均 **401**（到达上游，仅缺真 Key）——CORS 问题消除

### 3.4 高级设置（图一）

添加/编辑模型表单新增「高级设置」折叠区：
- **API 格式**下拉：OpenAI 兼容 / Anthropic Messages
- **模型能力**：工具调用 / 图片输入 / 推理（声明位，供选型提示）
- **输入（上下文）**：32K / 64K / 128K / 256K
- **输出**：8K / 16K / 32K / 64K（即 max_tokens 上界）
- 类型扩展：`ConfiguredModel.{apiFormat, capabilities, contextWindow, maxOutput}`；`addModel` 增加 `extras` 参数

### 3.5 群聊降级（图六修复）

激活模型失败时**自动换其他家人就绪绑定重试一次**，成功即用，失败才报错并注明「已尝试降级」。
**实证**：激活 GLM（假 Key）→ 401 → 自动降级家人绑定的 NAS nemotron → **200 + 千行真实回复**（请求链两条完整可见）。

### 3.6 只读纪律（AI 智能-模型管理）

移除：添加模型、导入、自定义服务商、服务商编辑/删除、模型删除、一键预设模型、AddModelModal/ProviderEditorModal 写模态。
保留：模型测试、只读列表、导出（只读快照）、Stats、Ollama 刷新。
新增只读横幅：「🔒 只读视图 · 编辑请前往「系统管理 → 模型设置」」。

## 五、遗留与口径

- **GLM Key 有效性**：截图 key（3e1a7d…）不在本机，无法代验；反代已消除 CORS，主控在系统设置重测试一次即可确认（若 401 需换 key）
- **"deepseek-flash / deepseek-v4-pro" 模型名**：DeepSeek 官方目录为 `deepseek-chat`/`deepseek-reasoner`；若上游不接受该名会返回明确诊断（模型名不被接受），需在系统中更名为官方名或走自建网关
- **模型能力旗标**为声明位：不改变协议行为（工具调用/视觉需上游支持与调用方实现）
- Mimosa 提示 i18n enterApiKey×2 / 消息 ID 弱随机：UI 文案与标识符，非真实凭据，口径不变
