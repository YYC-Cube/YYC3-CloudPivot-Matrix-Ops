## 一、现场事实（先分清「Key 问题」与「上游不可达」）

主控截图里 DeepSeek / GLM / Ollama 均为「已激活」且真实测通（1401ms），说明**面板链路本身是通的**；YYC³（家人分配）为红点。实测：

| 探测 | 结果 | 结论 |
| ---- | ---- | ---- |
| Tailscale `yyc3-45-1`（100.65.172.88） | active，ping 0.9ms | 主机在线 |
| NAS 网关 `:8000` | **ECONNREFUSED** | 网关服务未监听（不是 vk） |
| `api.0379.world/v1/models` | **502 Bad Gateway** | 公网入口在，回源 502 |
| `:8080 / :8001 / :8081 / :8888 / :9000` | 其他服务（Nexus / Web UI / nginx / mediamtx / MinIO） | 不能替代网关 |
| 3118 → NAS 反代 | 502 `connect ECONNREFUSED 100.65.172.88:8000` | 面板如实反映上游故障 |

「提示拦截」的真实语义（网关侧代码）：
- 输入 guardrail → HTTP 400 `输入违反内容安全策略: …`；
- 输出 PII guardrail → HTTP 400 `输出违反内容安全策略: 疑似泄漏邮箱/手机号/证件号…`（**回答里出现邮箱等即整条被拦**）；
- vk 无权访问模型 → 403 `虚拟密钥无权访问模型 X`；预算 → 402；TPM → 429。

以上都与「Key 字符串是否正确」不是一回事；原面板把原始 body 截 200 字直接展示，容易被读成「Key 被拦截」。

## 二、四个缺陷与修复

### 1. 服务商级 Key 未传播到模型（根因）

`updateProvider` 只同步 `label/baseUrl`，不同步 `apiKey`；模型仍带空 Key 或旧 Key。于是「服务商面板填了 Key、行上显示已激活」但真实请求不带新 Key——正是「密钥换了还是不通」。`FamilyModelSettings` 更只写「该服务商第一个模型」。

修复（`provider-slice.ts` / `FamilyModelSettings.tsx`）：
- `updateProvider` 检测 Key 变更后，对「空 Key 或等于旧服务商 Key」的模型同步新 Key；模型级独立 Key 不覆盖。
- `addModel` 未填 Key 时继承服务商级 Key。
- 家人「API 密钥管理」改写服务商级 Key（经上述传播生效）；Key 展示聚合服务商级与模型级。

### 2. 系统设置里没有「数据源」入口

`/sources` 只在主导航；主控在「系统设置」左侧 14 项里找不到。修复：`SystemSettings` 第 5 项新增「数据源」页签（中英文 i18n 同步），页签内嵌同一组件。

### 3. 数据源改地址不参与真实调用

原页面改 URL 只改注册表，NAS/DGX 上游仍来自 `deploy/server.mjs` 的 env。修复：
- `server.mjs` 新增 `GET / PUT /api/config/sources`：读取/写入运行态上游，**立即生效**；
- 持久化 `deploy/.sources.json`（tmp + rename 原子写，只存地址，不含凭据）；
- 校验：仅 http/https、禁止内嵌凭据；NAS/DGX/Ollama 必须本机/局域网/Tailscale；zhipu/deepseek 仅允许固定域名且 https；
- 反代改为协议感知（原写死 `http.request`，https 上游会打错协议）；
- 数据源页保存 NAS/DGX/Ollama 地址时 PUT 到 3118；行内显示「生效：3118 反代 → …」；Ollama 同址写回 provider，避免第二套事实源。

### 4. 服务商没有编辑面板、上游错误不可读

数据源页新增「模型服务（凭据唯一事实源）」：
- 增删服务商、改 `baseUrl / apiKey / 目录模型 / 是否需要 Key`；
- 「真实测试」走 `testConnection`（与聊天同一 `callConfiguredModel`）；
- 展开管理可增删模型实例（Key 继承服务商级）；
- Key 走 provider-slice 的加密 persist（落档 64），磁盘恒为 `yyc3enc1:` 信封。

`model-request.ts` 新增结构化错误解析与状态码解释：
- 400 guardrail → 「上游内容安全策略拦截（与 API Key 无关）」；
- 401 → Key 未送达/失效；403 model_not_allowed → 该 Key 未授权此模型；402 预算；429 限流；
- 502/504 → 「本地反代不可达：上游未启动或地址错误（系统管理 → 数据源 可改并立即生效）」。

### 附带：反代基址同源化

`resolveRequestRoot` 对写死 `localhost/127.0.0.1` 的 `/api/v1/llm/*` 基址按当前页面 origin 重写——两块办公地（静态 IP / Tailscale）或局域网设备访问时，`localhost` 不再指向客户端自己。

## 四、主控仍需做（与代码无关的三件事）

1. **启动 NAS 网关 `:8000`**（或在数据源页把 NAS 地址改到实际端口）。网关 down 时任何 vk 都不会通。
2. 在「系统设置 → 数据源 → 模型服务 → YanYuCloudCube」录 vk；现在写服务商级 Key 会同步到名下模型。
3. 若网关返回 **400 guardrail**，那是内容安全拦截（如回答含邮箱），与 Key 无关；需要时在网关侧关闭 `GUARDRAILS_PII_ENABLED` 或调整白名单。

## 五、未接线（如实登记）

- `db` / `fs` 仍为「未接」；`reverse-proxy` 自身端口不可从页面改（它由部署命令决定）。
- 3118 运行态配置只覆盖 ollama/dgx/nas 与两家云端固定上游；不提供任意公网代理。
- 网关 guardrail 与 vk 模型白名单在 YYC3-0379-World 仓库/部署侧，本档只保证 B 端如实显示，不代改上游策略。

## 六、v1.0.1 主控裁定整改（2026-11-23）

主控复核两处纠偏，均已执行：

1. **「另一个 origin」判断错误**。我方检测跑在 ZCode 内置浏览器（独立浏览器 = 独立 localStorage），看到的是我自己的测试环境残留（3 条旧模型），**不是主控浏览器的存储**。主控浏览器一套存储、8 个模型、Key 都在（模型管理可见 sk-ffe…/3e1a7d… 掩码）——项目就是一个、一套。已撤除页面上据此写的「localhost/127.0.0.1 两套 localStorage」提示。
2. **「模型服务」块与模型管理重复，违反「一个项目一个内容」**。数据源页撤除整个模型服务块（provider 增删改测/模型实例管理），**模型与 API Key 的唯一编辑面 = 「系统管理 → 模型管理」**；数据源回归其本职——连接源台账（agent / OpsPanel / Ollama / NAS / DGX / 3118 反代）的增删改测与 3118 运行态上游接线。落档 65 的 Key 传播修复（updateProvider/addModel）不受影响——它修的是 provider-slice 数据层，模型管理页直接受益。

**现场闭环**：主控启动 NAS 网关 `:8000` 后复测——`3118 → NAS` 返回 **HTTP 401「Missing authentication credentials」= 上游可达、只差 vk**；数据源页 NAS 行测试 ✅ `HTTP 401 · 上游可达（凭据在「模型管理」维护）· 21ms · 运行态上游 http://100.65.172.88:8000`。下一步只需在「模型管理 → YanYuCloudCube 服务商详情」录 vk（Key 传播修复使其自动同步到名下模型）。

门禁（v1.0.1）：tsc 0E；lint 0 error；**280 文件 / 4729 用例全绿**；build ✓；E2E 数据源页复核通过。
