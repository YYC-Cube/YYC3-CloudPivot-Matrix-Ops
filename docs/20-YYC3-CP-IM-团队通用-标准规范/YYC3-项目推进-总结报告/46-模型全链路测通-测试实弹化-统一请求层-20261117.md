## 一、实测暴露的三处真缺陷（主控三图对应）

| # | 主控证据 | 根因 | 修复 |
| ---- | ---- | ---- | ---- |
| 1 | 图三 浮窗「API Key 认证: HTTP 500」 | 诊断传 `modelName: model.name`，而 `model.name` = `"nemotron-3.5-super-vl (YYC³)"` **显示串** → 被当 API model 发出 → 上游 500 | 诊断两站点改传 `cm.model`（真实名） |
| 2 | 图二 拉取「HTTP 401 Header 未收到 Authorization」 | Key 实际存在**模型**（cm.apiKey），服务商级（provider.apiKey）为空 → 拉取只读服务商级 → 不带 Key | Key 解析链：输入框当前值 > 服务商级 > **该服务商下任一模型级**；无 Key 前置拦截并给操作指引；401/403 提示可操作化 |
| 3 | 图一「智能配置」提示（取消 API 后的限制） | 取消浮窗 API 编辑后，用户可能选到**必然失败**的模型却无从得知 | `availableModels` 增加 `missingKey` 标记 → 模型行显示「缺Key」并提示去系统设置补充 |

## 二、架构根修：测试链路 = 聊天链路

**问题**：`provider-slice.testConnection` 走独立诊断引擎——直连 `baseUrl` + 恒 OpenAI 格式；聊天走 `resolveRequestRoot`（自动反代）+ `apiFormat` 分流。**两条链路必然产生「测试通过、聊天失败」**（图二/三 8ms 假阳性的深层原因）。

**修复**：
1. 抽出 **`src/app/lib/model-request.ts`**：`callConfiguredModel` + `resolveRequestRoot`（唯一路由决策点）迁出 family-ai-service，`family-ai-service` re-export 保持既有调用方不变；同时**解除 provider-slice ↔ family-ai-service 循环依赖**。
2. `provider-slice.testConnection` 改为**实弹**：非 Ollama 模型直接 `callConfiguredModel(model, [{user:"ping"}], {maxTokens:1})`——测试即真能用；Ollama 走 `/api/tags` 可达性。
3. 结果写回 `lastTestResult`（步骤/建议），`/models` 诊断台据此给修复指引。

## 三、上游模型发现三形态兼容

「从上游拉取模型列表」实测发现：NAS 网关 `/v1/models` 返回**裸数组** `[{id,name,backend…}]`，而 OpenAI 官方式为 `{data:[…]}`、Ollama 式 `{models:[…]}`。原解析只认后两者 → 空列表。现三形态全兼容（`id`/`name`/`model` 字段均可）。
**实证**：拉取成功 → chips 出现 `+ glm-4-flash`、`+ glm-4-plus`、`+ deepseek-chat` 等真实上游模型。
