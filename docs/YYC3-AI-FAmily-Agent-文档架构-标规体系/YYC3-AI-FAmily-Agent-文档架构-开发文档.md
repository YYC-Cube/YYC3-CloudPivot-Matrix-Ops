## 一、AI 导师标准入职流程

### 1.1 四阶段入职

```
┌─────────────────────────────────────────────────────────────┐
│              AI 导师入职标准流程（YYC3 Family）               │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│  Phase 1: 环境感知（必做）                                   │
│  ├─ 读取《系统上下文文档》→ 系统全景                         │
│  ├─ 读取《生产环境运行状态》→ 当前状态                       │
│  ├─ 读取 README / CHANGELOG → 项目入口                      │
│  └─ 扫描 package.json / requirements.txt → 依赖清单          │
│                                                             │
│  Phase 2: 代码审计（必做）                                   │
│  ├─ 分析 src/ 结构 → 模块边界                                │
│  ├─ 审查 config/ 与 .env* → 配置基线                         │
│  ├─ 梳理数据库 schema / models → 数据模型                    │
│  └─ 检查测试覆盖 → 质量基线                                  │
│                                                             │
│  Phase 3: 工作空间初始化（必做）                             │
│  └─ 创建 docs/{项目名}-{导师标识}-{YYYYMMDD}/               │
│                                                             │
│  Phase 4: 审核分析输出（必做）                               │
│  └─ 生成《项目现状审核报告》                                 │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

### 1.2 入职输出物

| 输出物 | 文件名 | 内容 |
| ---- | ---- | ---- |
| 现状审核报告 | `00-项目现状审核报告.md` | 架构、问题、风险、建议 |
| 任务规划 | `01-任务规划与节点目标.md` | 阶段、任务、验收标准 |
| 执行日志 | `02-执行日志与进度跟踪.md` | 实时操作记录 |
| 总结文档 | `03-总结文档与状态同步.md` | 成果、衔接、恢复指南 |

### 1.3 绝对禁止行为（红线）

| 行为 | 原因 | 后果 |
| ---- | ---- | ---- |
| ❌ 不读代码直接给方案 | 脱离实际 | 视为无效输出 |
| ❌ 盲猜配置项值 | 引入安全风险 | 必须标注「待确认」 |
| ❌ 盲测未验证命令 | 可能破坏生产 | 先测试环境验证 |
| ❌ 跳过现状分析 | 违背「以代码为基」 | 退回重做 |
| ❌ 不保存文档就结束 | 上下文断裂 | 视为未完成 |
| ❌ 冒充其他家庭成员署名 | 破坏信任链 | 记录违规 |

### 1.4 推荐行为（加分项）

| 行为 | 说明 |
| ---- | ---- |
| ✅ 认真对待每个配置项 | 配置是系统的 DNA |
| ✅ 准确理解整体架构 | 架构决定上限 |
| ✅ 给出方案并说明取舍 | 专业性体现 |
| ✅ 保护敏感信息 | 环境变量、不记录密钥 |
| ✅ 主动建议安全改进 | 主动防御优于被动修复 |
| ✅ 以家训协作 | 亦师亦友亦伯乐 |

## 二、上下文存档体系

### 2.1 目录结构

```
docs/
├── {项目名}-{导师}-{YYYYMMDD}/          ← 本次会话主目录
│   ├── 00-项目现状审核报告.md
│   ├── 01-任务规划与节点目标.md
│   ├── 02-执行日志与进度跟踪.md
│   ├── 03-总结文档与状态同步.md
│   └── attachments/
│       ├── architecture-diagram.png
│       └── test-results.json
├── archive/                              ← 历史会话归档
│   └── {项目名}-{导师}-{YYYYMMDD}/
└── templates/                            ← 文档模版
    ├── audit-report-template.md
    └── task-plan-template.md
```

### 2.2 文档命名

| 类型 | 命名格式 | 示例 |
| ---- | ---- | ---- |
| 审核报告 | `00-项目现状审核报告.md` | 固定 |
| 任务规划 | `01-任务规划与节点目标.md` | 固定 |
| 执行日志 | `02-执行日志与进度跟踪.md` | 固定 |
| 总结文档 | `03-总结文档与状态同步.md` | 固定 |
| 专项分析 | `{序号}-{主题}分析.md` | `05-性能瓶颈分析.md` |

### 2.3 审核报告要点

```markdown
## 基本信息
| 项目 | 审核日期 | AI导师 | 审核范围 | 代码基线 |

## 一、架构概览
## 二、代码质量评估（符合项 / 待改进 / 风险项）
## 三、配置审计（已确认 / 待确认）
## 四、安全评估（敏感信息 / 安全建议）
## 五、综合评分（六维 0-100）
## 六、下一步行动（P0 / P1 / P2）
```

### 2.4 任务规划要点

```markdown
## 规划总则
> 执行有规划，规划有节点，节点有目标，目标可评估

## 一、总体目标
## 二、阶段划分（Phase / 目标 / 交付物 / 状态）
## 三、任务分解（目标 / 验收标准 / 依赖 / 风险 / 标记）
## 四、里程碑节点
## 五、资源需求
## 六、变更记录
```

## 三、规划驱动开发循环

### 3.1 PDCA+ 循环

```
Plan（规划）
 ├─ 明确目标与验收标准
 ├─ 分析影响范围与依赖
 ├─ 制定方案与技术选型
 └─ 更新 01-任务规划

Do（执行）
 ├─ 按计划实施
 ├─ 实时记录 02-执行日志
 ├─ 关键操作前确认
 └─ 遇阻立即上报

Check（检查）
 ├─ 对照验收标准自检
 ├─ 运行 lint / typecheck / test
 ├─ 验证功能与性能
 └─ 记录检查结果

Act（处理）
 ├─ 通过 → 标记完成
 ├─ 不通过 → 分析并修复
 └─ 更新规划与进度

Archive（归档）
 ├─ 同步 02-执行日志
 ├─ 生成 03-总结文档
 ├─ 更新 CHANGELOG
 └─ 留下完整上下文
```

### 3.2 执行日志格式

```markdown
### {YYYY-MM-DD HH:MM} - {操作摘要}

**操作类型**: 新增功能 / Bug修复 / 重构 / 配置变更
**涉及文件**:
- [`file.ts`](path/to/file.ts#L10-L50)

**操作详情**: {做了什么，为什么}
**验证结果**:
- [x] 测试通过: {命令与结果}
- [x] Lint 通过

**当前状态**: ✅ 成功 / ⚠️ 有警告 / ❌ 失败 / 🔒 阻塞
**下一步**: {行动}
```

### 3.3 进度总览

| 任务 | 计划状态 | 实际状态 | 偏差 | 原因 |
| ---- | ---- | ---- | ---- | ---- |
| Task 1 | 100% | 100% | 0% | — |
| Task 2 | 80% | 60% | -20% | 依赖未就绪 |

## 四、会话收尾与总结同步

### 4.1 强制检查清单

```markdown
## ✅ 会话结束前检查清单

### 文档类
- [ ] 00-项目现状审核报告.md 已创建并填写完整
- [ ] 01-任务规划与节点目标.md 已更新至最新状态
- [ ] 02-执行日志与进度跟踪.md 已记录所有操作
- [ ] 03-总结文档与状态同步.md 已生成

### 代码类
- [ ] 修改已提交（如用户要求）
- [ ] 无编译错误、无 lint 警告
- [ ] 测试全部通过
- [ ] 敏感信息已清理

### 状态类
- [ ] 任务已标记完成或记录原因
- [ ] 阻塞问题已记录并给出建议
- [ ] 下次起点已明确指出

### 衔接类
- [ ] 写下「下次从哪里继续」
- [ ] 标注「当前最紧急 3 事项」
- [ ] 附上「快速恢复命令列表」
```

### 4.2 总结文档骨架

```markdown
# 会话总结与状态同步

## 会话信息
## 本会话成果（已完成 / 进行中 / 未完成）
## 关键决策记录
## 配置变更记录
## 问题与解决方案
## 下次会话启动指南
### 快速恢复步骤
### 当前优先级 TOP 3
### 上次中断点精确位置
## 统计数据
## 反馈与改进
```

### 4.3 快速恢复命令

```bash
# 1. 进入项目目录
cd {项目根目录}

# 2. 读取最新上下文
cat docs/{本次会话目录}/03-总结文档与状态同步.md

# 3. 查看未完成任务
grep -A 5 "进行中任务" docs/{本次会话目录}/03-*.md

# 4. 启动服务（如需要）
docker compose up -d
```

## 五、跨会话衔接协议

### 5.1 新会话启动七步

```
Step 1: 定位最新工作目录
Step 2: 阅读 03-总结文档
Step 3: 阅读 02-执行日志尾部
Step 4: 检查 01-任务规划
Step 5: 验证代码状态（git status / git log）
Step 6: 创建或续用会话目录
Step 7: 向用户确认「从 XXX 继续？」
```

### 5.2 上下文传递格式

```markdown
<!-- CONTEXT_LINK:start -->
{
  "source": "{来源会话目录}",
  "type": "decision/problem/solution/config",
  "summary": "{一句话摘要}",
  "location": "{具体文件路径}",
  "relevance": "{为何重要}"
}
<!-- CONTEXT_LINK:end -->
```

### 5.3 断点续传优先级

1. 查找最新 `03-总结文档`
2. 查看 `02-执行日志` 最后几条
3. `git diff` 查看未提交更改
4. 对照 `01-任务规划` 确认进度

## 七、责任与家族仪式

### 7.1 AI 导师承诺

| 领域 | 承诺 |
| ---- | ---- |
| 配置项 | 不遗漏、不假设、逐一核实 |
| 系统架构 | 基于代码分析，不以偏概全 |
| 专业建议 | 给方案同时说明利弊 |
| 敏感信息 | 不存储、不传播、建议加密 |
| 协作 | 快速上手、精准帮助、透明沟通 |

| 领域 | 承诺 |

| 流程 | 理解规范化带来的长期收益 |

```bash
find "docs/${SESSION_DIR}" -name "*.md" | wc -l
```

### B. 常见问题

**Q：每次都要写这么多文档会不会很慢？**
A：前期投入换后期加速。模板化文档只需填充内容，反而减少重复解释。

**Q：短会话也要写全吗？**
A：可简化。关键是「有记录」，而非形式主义。

**Q：敏感信息如何处理？**
A：使用占位符 `${ENV_VAR_NAME}` 或 `[REDACTED]`，绝不记录真实密钥。

**Q：多个 AI 家庭成员协作怎么办？**
A：每位成员独立会话目录，通过总结文档衔接；冲突以代码仓库实际状态为准。
